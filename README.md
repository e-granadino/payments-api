# Payments API

Technical assessment implementation for a Java Integration Engineer
role.

The project provides a REST API for creating and querying payments,
persists data in Oracle, transforms accepted payments to XML for a
core-system integration boundary, includes SQL/PLSQL deliverables, and
provides a Python automation script that generates a customer payment
summary CSV.

## 3.2 Payment creation flow

``` text
POST /api/v1/payments
        |
        v
PaymentController
        |
        v
PaymentService
        |
        +--> Create Payment
        |      status = PENDING
        |      createdAt = server generated
        |
        +--> Save to Oracle
        |
        +--> PaymentXmlMapper
        |
        +--> CorePaymentClient
                |
                v
        MockCorePaymentClient
```

The `CorePaymentClient` interface isolates the application from the
external core payment system.

Because the assessment does not provide a real core-system endpoint,
`MockCorePaymentClient` is used as the local implementation. It logs the
XML payload that would be sent to the core system.

A real REST, SOAP, messaging, or other adapter could replace this
implementation without changing `PaymentService`.

## 3.3 REST API design

The API uses resource-oriented REST naming.

The same resource URI is intentionally used for different HTTP
operations:

``` text
POST /api/v1/payments
GET  /api/v1/payments
```

The HTTP method identifies the operation while `/payments` identifies
the resource.

### Create payment

``` http
POST /api/v1/payments
Content-Type: application/json
Authorization: Basic <credentials>
```

Request:

``` json
{
  "customerId": "CUS-001",
  "amount": 150.75,
  "currency": "USD"
}
```

The client does not provide `status` or `createdAt`.

-   New payments start with `PENDING`.
-   `createdAt` is generated by the server.

Successful response:

``` json
{
  "success": true,
  "data": {
    "id": "9a7f7c0d-7c45-4c36-a8e2-2f9a2c7e1b44",
    "customerId": "CUS-001",
    "amount": 150.75,
    "currency": "USD",
    "status": "PENDING",
    "createdAt": "2026-09-23T10:00:00Z"
  }
}
```

HTTP status: `201 Created`.

### Query payments

Both `from` and `to` are required query parameters.

``` http
GET /api/v1/payments?from=2026-09-01T00:00:00Z&to=2026-09-23T23:59:59Z
Authorization: Basic <credentials>
```

An optional customer filter can be supplied:

``` http
GET /api/v1/payments?customerId=CUS-001&from=2026-09-01T00:00:00Z&to=2026-09-23T23:59:59Z
```

The service rejects a range where `from` is after `to`.

------------------------------------------------------------------------

## 3.4 Response and error handling

Successful responses use a consistent wrapper:

``` json
{
  "success": true,
  "data": {}
}
```

Errors use a consistent structure containing timestamp, HTTP status,
error, message, path, and validation details.

The centralized `GlobalExceptionHandler` handles, among others:

-   Bean validation failures
-   Malformed JSON
-   Invalid query parameter values
-   Invalid date ranges
-   Missing required query parameters
-   Authentication failures

# 5. Database

Oracle is the primary database.

## 5.1 Data model

``` text
CUSTOMERS
---------
ID
NAME
COUNTRY

PAYMENTS
--------
ID
CUSTOMER_ID
AMOUNT
CURRENCY
STATUS
CREATED_AT

PAYMENT_PROCESSING_LOG
----------------------
ID
PAYMENT_ID
ERROR_CODE
ERROR_MESSAGE
ERROR_TIMESTAMP
```

`PAYMENTS.CUSTOMER_ID` references `CUSTOMERS.ID`.

Payment IDs are represented as UUIDs in Java and stored as `RAW(16)` in
Oracle.

Amounts use `NUMBER(19,4)` and payment creation timestamps use
`TIMESTAMP WITH TIME ZONE`.

## 5.2 Schema owner and application user

The Oracle schema owner is:

``` text
ORG_BDO
```

The application connects using:

``` text
APP_USER
```

This intentionally separates the application account from the schema
owner.

Hibernate uses:

``` properties
spring.jpa.properties.hibernate.default_schema=ORG_BDO
```

The schema can therefore be overridden without changing application
code.

## 5.3 Hibernate schema strategy

The application uses:

``` properties
spring.jpa.hibernate.ddl-auto=validate
```

Hibernate validates the schema rather than creating or modifying
database objects.

Database structure is managed through SQL scripts.

# 8. Challenge Part 2 - SQL and PL/SQL

The SQL/PLSQL deliverables are under:

``` text
scripts/part2/
├── 01-top-customers.sql
├── 02-process-pending-payments.sql
└── 03-indexes.sql
```

## 8.1 Top 10 customers

`01-top-customers.sql` returns the 10 customers with the highest total
amount paid during the last 30 days.

The query includes:

-   Customer ID
-   Customer name
-   Country
-   Total amount paid
-   Payment count
-   Average ticket

Only `PROCESSED` payments are considered paid because `PENDING`
represents payments that have not completed processing.

The query uses:

``` sql
p.CREATED_AT >= SYSTIMESTAMP - INTERVAL '30' DAY
```

and:

``` sql
p.STATUS = 'PROCESSED'
```

The result is grouped by customer and ordered by total amount
descending.

## 8.2 Pending payment processing

`02-process-pending-payments.sql` defines:

``` text
PROCESS_PENDING_PAYMENTS
```

The procedure:

1.  Finds payments with `PENDING` status.
2.  Locks the rows for processing.
3.  Changes successful payments from `PENDING` to `PROCESSED`.
4.  Handles exceptions at the individual-payment level.
5.  Records processing errors in `PAYMENT_PROCESSING_LOG`.
6.  Uses a savepoint so an individual failure does not roll back
    successfully processed payments.
7.  Uses an outer exception handler for unexpected procedure-level
    failures.

The error log stores:

``` text
PAYMENT_ID
ERROR_CODE
ERROR_MESSAGE
ERROR_TIMESTAMP
```

## 8.3 Index

`03-indexes.sql` creates an index supporting the top-customers query:

``` sql
CREATE INDEX IDX_PAYMENTS_STATUS_CREATED_CUSTOMER
    ON PAYMENTS (
        STATUS,
        CREATED_AT,
        CUSTOMER_ID
    );
```

The index is designed around the query's filtering and join conditions:

``` text
STATUS       -> equality filter
CREATED_AT   -> 30-day range filter
CUSTOMER_ID  -> customer join
```

The actual optimal index can depend on data distribution and the Oracle
execution plan; the script documents why this index is relevant to the
required query.

# 9. Challenge Part 3 - Python Automation

The Python deliverable is:

``` text
scripts/part3/payments_report.py
```

It consumes:

``` text
GET /api/v1/payments
```

using Basic Authentication and generates a CSV summary per customer.

## 9.1 Output

The generated CSV contains:

``` csv
customer_id,total_amount,payment_count,average_payment
CUS-001,1250.50,5,250.10
CUS-002,850.00,3,283.33
```

The calculations use Python's `Decimal` type rather than floating-point
arithmetic because the script processes monetary values.

## 9.2 Configuration

The script supports environment variables:

``` text
API_URL
API_USERNAME
API_PASSWORD
FROM_DATE
TO_DATE
OUTPUT_FILE
```

Default local values are:

``` text

FROM_DATE=2026-09-01T00:00:00Z
TO_DATE=2026-09-23T23:59:59Z
OUTPUT_FILE=payments-report.csv
```

Command-line arguments can override these values.

## 9.3 Running the script

From the project root:

``` bash
python scripts/part3/payments_report.py
```

Specify a date range and output file:

``` bash
python scripts/part3/payments_report.py \
    --from-date 2026-09-01T00:00:00Z \
    --to-date 2026-09-23T23:59:59Z \
    --output payments.csv
```

On Windows PowerShell, the same command can be written on one line:

``` powershell
python scripts/part3/payments_report.py --from-date 2026-09-01T00:00:00Z --to-date 2026-09-23T23:59:59Z --output payments.csv
```

## 9.4 Error handling

The script handles errors without exposing a Python traceback to the
user.

Handled cases include:

-   Authentication failure (`401`)
-   Access denied (`403`)
-   Other HTTP errors
-   Connection failures
-   Connection timeout
-   Invalid JSON
-   Invalid API response structure
-   Missing customer ID
-   Invalid payment amounts
-   CSV file write errors

Errors are written as concise messages to stderr and the script exits
with a non-zero status.

## 9.5 Python dependencies

The script intentionally uses only the Python standard library.

No:

``` bash
pip install ...
```

is required.

This keeps the Part 3 deliverable simple and portable.

-   Payment creation
-   `PENDING` initial status
-   Server-generated `createdAt`

-   Payment-to-response mapping

Tests cover:

-   Successful payment creation
-   Payment queries
-   Customer/date filtering

-   Malformed JSON

# 14. Design Decisions

## Why Basic Authentication?

The assessment allows Basic Authentication or JWT.

Basic Authentication was selected because the assessment does not
require an identity provider, token endpoint, refresh-token lifecycle,
or role-based authorization model. It provides the required protection
with minimal additional infrastructure.

## Why `PENDING` as the initial status?

New payments start as:

``` text
PENDING
```

The Part 2 processing procedure subsequently transitions eligible
payments to:

``` text
PROCESSED
```

## Why is `createdAt` generated by the server?

`createdAt` represents when the application creates the payment. It is
therefore generated by the application instead of being accepted from
the client.

This prevents clients from arbitrarily setting a system-controlled
creation timestamp.

## Why use the `CorePaymentClient` interface?

The assessment requires an accepted payment to be transformed to XML and
sent to a core system, but no real core-system endpoint is provided.

The interface:

``` java
CorePaymentClient
```

isolates that external dependency.

The current local implementation:

``` text
MockCorePaymentClient
```

logs the generated XML.

A production implementation could replace it with a REST, SOAP, Kafka,
or other adapter without changing the payment service contract.

## Why use `ddl-auto=validate`?

The database schema is explicitly defined by SQL scripts. Hibernate
should validate the schema rather than silently create or modify
database objects.

## Why keep Docker Compose?

They serve different purposes.

Docker Compose provides a convenient persistent Oracle instance for
local development.

## Transaction and external integration consideration

Payment persistence and core-system delivery currently happen
synchronously.

The project intentionally does not implement an Outbox Pattern because
that is outside the scope of the assessment.

In a production system where guaranteed delivery and
database/external-system consistency are critical, an Outbox Pattern or
equivalent reliable messaging mechanism could be considered.
